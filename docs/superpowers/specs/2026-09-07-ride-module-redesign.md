# 漫途 · 骑行模块重构设计方案（聪明骰子）

> 日期：2026-09-07
> 范围：`ExploreView`（路线探索）/ `PresetView`（经典路线）/ `useRouteEngine`（生成引擎）/ 新增廊道数据层
> 关联现状文档：`docs/superpowers/specs/2026-07-23-randompath-ux-redesign.md`（旧的交互改造，已被本方案取代）

---

## 1. 背景与动机

漫途是一款以「随机探索骑行路线」为魂的 PWA（Vue 3 + 高德骑行 API + Canvas 缩略图），骑行模块现状是「点随机 → 高德选路 → 折返修复 → 出结果」。作为软件策划兼资深骑手（熟悉陕西秦岭、骊山、渭河河堤等路线）审读源码后，当前"不好用"的根因不在 UI 排布，而在三层结构性错位：

| 症结 | 表现 | 根因（代码证据） |
|------|------|------|
| 里程说了不算 | 环线要 20km 实际给 11~30km | `ExploreView.vue:275` 容差 `0.55×~1.5×` |
| 爬升常为空 | 正常生成的路线爬升永远 `--` | `useRouteEngine.js:482-483` 命中即 return，只有 12 次全失败走兜底才跑坡度分析（`496-509`） |
| 爬升失真 | 即便算了也把山抹平 | `useRouteEngine.js:313` 全路线最多 20 采样点；`339` 约 400m 一步、阈值 5% |
| 难度瞎标 | 分水岭 30km 被标「休闲」 | `useScoring.js` 用空爬升套距离表 |
| 不认路况 | 随机往大车国道/隧道带 | `useRouteEngine.js:531` 只用步骤文本正则猜避让 |
| 方向失控 | 想刷秦岭却把你推去渭北 | `ExploreView.vue:266` 环线朝向写死 `dirDeg=null` 纯随机 |
| GPX 偏移 | 导码表整体偏 300~500m | `useRouteEngine.js:546` GCJ-02 当 WGS84 直出 |
| 预置库僵尸化 | 大量 300~700km 跨省穿越、徒步线硬安骑行 | `PresetView.vue` 数据无难度/爬升/信任字段 |
| 交互不对序 | 骑车人决策序「多远→什么路→往哪」缺「什么路/往哪」输入 | `SceneCards.vue` 只有目的地/距离两卡 |

**一句话结论**：工具眼里只有「地图上的随机点」，而骑行要的是「一条能预判、敢托付的好路」。本方案把「随机」从全地图乱滚的骰子，改成**在「好路信封」里抽盲盒**。

## 2. 目标与非目标

### 目标
1. **魂不变**：仍是随机探索，绝不退化成"翻精品库"的路线本。随机 = 每趟组合都不同。
2. **每条滚出来的路先是条好路**：生成结果落在"可骑廊道 + 路况语义"的场子里，大车国道/烂路/禁行段进不来。
3. **数据说人话**：爬升、坡度、难度真实可信；廊道带**信任分级**，不装懂。
4. **地盘全省**：陕西关中/陕南/陕北都纳入，按起点自动落到本地玩法池。

### 非目标（明确不做）
- 不做多日/跨省长途的"随机生成"（西安→榆林 600km 那类留在路线库按"长途挑战"浏览，单车 API 规划不动，也不该随机）。
- 不做社交/组队（v1）。
- 不把现有 100 条预置线当垃圾删掉——它们是廊道自动重建的原料。

## 3. 现状诊断与保留清单

### 3.1 该保留的硬家当（不重写）
- 高德真实骑行规划 + 逆地理编码智能起名（`useRouteEngine.js:562`）
- 折返/死胡同检测与"吸附回主路"修复思路（`useRouteEngine.js:146-273`）
- 结果页三大件（缩略图/爬升曲线/分段表）+ 导航/GPX/分享/PWA（`ResultView.vue`）
- 补给点沿路搜索、村庄地名识别（`useRouteContext.js`）
- LocalStorage 地址簿/历史/冷却区防重复的整套模式（`useStorage.js`）

### 3.2 该拆掉的旧逻辑
- `useScoring.js:scoreRoute` 引用的 `maxSlope/steepKm*/uninhabitedKm` 字段从未被填——死代码，删或等坡度数据真实后再接线。
- `SceneCards`「指定距离环线」把地形/方向藏没了的输入模型。
- 生成命中也跳过坡度分析的分支结构（`tryGenerateRoute` 需重构为"必经坡度分析"）。

## 4. 决策记录（已与 owner 拍板）

| 决策点 | 结论 |
|--------|------|
| 服务范围 | **陕西全省**（关中/陕南/陕北），按起点自动落本地玩法池 |
| 产品主玩法 | **保留随机探索为魂**；随机=换着花样组"好路" |
| 廊道数据来源 | **自动重建 + 信任分级**：现库 100 条预置线 + 高德骑行路网离线切片成候选廊道，先标"灰·待实测"；实骑/导入轨迹命中再升级"绿·实测" |
| 生成架构 | **聪明骰子（方案甲）**：语义加权随机，廊道库做"好路信封"；模板环只作稀疏区兜底出口 |

## 5. 总体架构

```
┌──────────── 运行时（浏览器） ────────────┐
│  Explore（4步出题）──> 聪明骰子引擎 ──> 3条候选   │
│        │                    │                   │
│  RouteLibrary（路线库）   （读 静态 JSON）          │
└──────────────┬─────────────────────────┘
               │ 仅家->廊道引道 / 断口补路 走高德API
┌──────────────▼─────────────────────────┐
│        高德骑行规划 / 逆地理 / POI          │
└─────────────────────────────────────────┘
        ▲ 一次性离线构建（不进运行时）
┌────────┴────────┐
│ build-corridors.mjs │──> data/corridors.js + data/playpools.js（静态）
│ 现库100预置线 切片  │
└────────────────────┘
```

核心思路：**把"好路的先验知识"从运行时挪到静态数据**。骑行 90% 的信任问题来自"临时现场发挥"，把可信路段建成静态账本，运行时只做组合与连接，不再让骰子在全地图乱掷。

## 6. 数据模型

### 6.1 廊道 `corridor`（一条"单独值得骑的路"）

```js
{
  id: 'qinling-fengyu-1',          // 区域-段名-序
  region: '关中南',                 // 关中/陕南/陕北 + 子区
  name: '沣峪口→分水岭（G210爬坡）',
  type: 'climbRoad',               // greenway|riverDyke|climbRoad|countyRoad|urban
  surface: 'paved',                // paved|gravelLite|offroad
  climbBand: 'hill',               // flat|rolling|hill|epic
  playpool: ['nan-ling'],          // 归属玩法池 id 列表
  distKm: 33.0, endKm: 0,
  climbM: 0,                       // P1 由构建脚本 + 修正采样真实计算；P0 前允许空
  start: { lng, lat, name },       // GCJ-02
  end:   { lng, lat, name },
  geo: '…polyline 压缩串…',         // 高德规划 polyline（供缩略图/坡度）
  trust: 'grey',                   // grey|yellow|green|blue，见 6.3
  flags: ['heavyTruck?','tunnel?','gap'], // 自动避让词筛查出的疑点
  supplyDensity: 0.3,              // 每公里补给点密度（0~n，可后补）
  src: 'preset:西安·秦岭分水岭',       // 来源标注，可追溯
  curatedBy: '',                   // 'human-<name>' 人工精校标记
  checkedOn: '2026-09-07',
  status: 'open'                   // open|blocked|construction（封路/施工，运营期维护）
}
```

### 6.2 玩法池 `playpool`（骑行语义归堆）

```js
{
  id: 'nan-ling',
  region: '关中南',
  label: '南山·峪口爬坡',
  desc: '秦岭北麓各峪口、分水岭方向，坡多为折返',
  anchors: ['沣峪口','子午大道','环山路S107'], // 锚点地名，便于搜起点
  corridorIds: [...],             // 引用而非内嵌，保持单一事实源
  defaultShape: 'outback',        // 该池默认 环线|折返|单程
  defaultBand: 'hill',
  coverId: 'qinling-fengyu-1'     // 池封面廊道（列表/缩略用）
}
```

### 6.3 信任等级（不装懂，界面可见）

| 级 | 色 | 含义 | 准入 |
|----|----|------|------|
| grey | 灰·自动 | 现库途经点之间自动重建，未经实骑 | 随机默认**不优先**；仅勾"允许待实测"或"随缘"时进入 |
| yellow | 黄·疑似 | 过避让词筛查仍有疑点（隧道/大车/几何残） | 随机**优先信封**默认线 |
| green | 绿·实骑 | 与实骑轨迹/人工确认匹配 | 始终可入 |
| blue | 蓝·精校 | 逐字段人工校验过（含补给/封路状态） | 始终可入 |

随机信封默认门槛：**yellow 及以上**。「只要实测」开关 → 仅 green/blue。

### 6.4 构建脚本（离线一次性，不进运行时）

`scripts/build-corridors.mjs`：
1. 遍历现库 `PresetView.vue` 的 `PRESET_ROUTES` 全部途经点序列。
2. 对相邻途经点对调高德骑行规划（开发期带 key 跑），得 polyline 与里程 → 一条候选廊道。
3. 跑避让词筛查（复用 `fetchOptimalBikeRoute` 的 `BAD_ROAD_RE` 思路，扩到隧道/高速/城市快速/立交/「禁行」），命中打 `flags`、降 `yellow`。
4. 按起终点吸附去重（相邻端点 <60m 合并），同一段多次命中取中值。
5. 单段 >40km 或 API 失败的：标记为"长途/不可用"，不进随机信封，仅留在路线库。
6. 产出 `data/corridors.js`、`data/playpools.js`（静态，随构建打包）。
7. 全程节流（沿用 200~600ms 间隔），跑完输出统计：总段数 / 各区域分布 / 灰黄占比，供后续补齐。

> 注：关中以外（陕南/陕北）预置线稀疏，首轮重建后灰段多属正常——随机引擎在该区默认放低"必须成闭环"的执念，多出折返/单程候选。

### 6.5 廊道图与起点接入
- 廊道端点吸附成无向图节点，廊道为边（后续算法第 3 步用）。
- 起点（家/GPS）不在图上时：以起点为中心就近找图上可达节点（高德逆地理/POI 定位到最近锚点），"家→图"与"图→家"两段引道单独走高德规划，计入门对门总里程。

## 7. 交互与信息架构（Explore 重排）

### 7.1 四步出题（取代"两张模式卡"）

```
① 从哪出发   起点卡（GPS/地址簿/搜索）沿用
② 骑多远    里程档 10/20/30/50/80/100（可自定义）
            旁挂实时耗时：平路按18km/h、爬坡按13km/h（不再一个速度打天下）
③ 什么路    平路巡航 / 起伏有致 / 爬坡过瘾 / 随缘
            选"爬坡过瘾"即给引擎设爬升预算上限约束
④ 往哪边    随缘 / 依起点列出 3~5 个玩法池
            （起点在西安列秦岭·骊山·渭河·渭北·城郊绿道；
              在汉中立列汉中·巴山等 → 全省通用）
高级（折叠） 避让：禁大车国道/隧道/高速（默认开）
            最大单段里程、信任门槛（只要实测绿蓝 / 允许黄 / 允许灰）
```

### 7.2 结果（一次 3 条候选）
- 每张候选卡顶格亮：**距离 · 爬升 · 路型 · 玩法池 · 信任徽章**。
- 点入明细沿用 `ResultView`：爬升曲线、坡度段、分段表、补给密度；动作栏：导航 / GPX / 分享 / 收藏我的路线。
- **钉段局部重掷**：可锁定某一段（勾选），点"换一条"只重掷其余段——不再整个推倒。
- 选择"环线/折返/单程"由地形自动定，折返类在卡片上明示"去程返程同路，终点折返"。

### 7.3 路线库（PresetView 改造）
- 预置线升级为带实测数据的"线路条目"：预存距离/爬升/坡度/难度/信任。
- 加筛选：玩法池 / 里程 / 爬升 / 难度 / 信任级；保留现有搜索与自定义起点。
- 每条库线给两条路：「骑这条」和「**当灵感**」——把该线途经点作种子塞回随机引擎生成变体，打通库与生成器。

## 8. 生成算法（聪明骰子）

输入：起点 P、目标里程带 `[dMin,dMax]`（默认 ±12%，可兜底放宽到 ±15%）、地形档、玩法池（或随缘）、避让/信任约束。

```
1. 取信封：按 地形档+信任门槛+玩法池 过滤廊道集 E；随缘则多池并集。
2. 建图：E 内端点吸附(<60m)成节点；起点 P 就近接入（见 6.5）。
3. 选形：依据玩法池 defaultShape 与地形——爬山→折返(outback)，
         绿道/河堤/平原→环线，支持池内 point2point。形状可被用户锁定。
4. 图上游走（DFS/回溯，深度≤6）：
   目标：环线=回 P；折返=到最远节点后沿原廊道回（去返可微差）；
   边权累计 dist+climb；一边游走一边按 [dMin,dMax] 与最大单段剪枝。
5. 连通：选中廊道序列的断口、以及 P↔图引道，走高德骑行规划补实，合并 polyline。
6. 老闸门（全保留）：折返/死胡同检测与吸附修复、避让词、冷却区防重复、
   信任过滤——任一不过即弃（本候选），由步骤 4 重走。
7. 野趣（保持惊喜）：小概率在选定廊道中途选一个"周边乡道/小众 POI 岔口"
   作途经点（复用 nameWaypoint），能过闸才放行，过不了就老实待在信封里。
8. 达标判定收紧：总里程落在目标带内（默认 ±12%，兜底放宽 ≤±15%）才算成；不成则记 best 继续换种子。
9. 打分排序取前 3：滨水/绿荫/清净(复用 scoreRouteQuality) + 补给密度
   + 与最近骑过(冷却表)的差异 + 形状自然度(折返不绕路)。
10. 全程必做坡度分析（见 9.1），真实爬升/坡度进候选卡与难度评级。
```

每趟组合随种子变化 → 盲盒惊喜；但每一块的原料都先是一条好路 → 信任保住。

## 10. 错误处理与边界

- **廊道稀疏**（地图数据残缺区）：降级为"模板兜底"（该区现库最接近目标的 1~2 条线整段作候选）并明示"这是保险线"；再不行给出"该区暂无法合成，请选其他玩法池或去路线库"。
- **高德 API 失败/限流**：沿用现有退避重试与缓存；静态廊道库本身不受运行时 API 影响，家→图引道失败时允许"仅信封内成环"（无引道）。
- **爬升接口不可用**：P0 后是硬依赖，失败须 toast 明确，不让空数据冒充"平路"。
- **信任门槛组合无解**：提示放宽（允许灰/放宽里程带），给回退按钮，不静默乱出。

## 11. 落地路径

### P0 · 数据止血（独立可先上）
9.1~9.5 + `useScoring` 死字段清理。改动集中在 `useRouteEngine.js` / `useScoring.js` / 少量视图。可配测试：见 §12。

### P1 · 聪明骰子 v1（西安—关中先跑通）
1. `data/corridors.js` schema + `data/playpools.js` + 6 个关中玩法池定义。
2. `scripts/build-corridors.mjs` 跑关中片 → 静态 JSON 入库（前端 import）。
3. `useRouteEngine` 重构为"信封+图游走+连通+闸门+必算坡度"；保留对外 API 形态以便视图小改。
4. Explore 四步出题 UI + 3 候选卡 + 钉段重掷；路线库筛选与"当灵感"。
